\# ADR-0013 — Object Storage para Armazenamento de Arquivos



\*\*Status:\*\* Aprovada



\*\*Versão:\*\* v1



\*\*Data:\*\* Julho de 2026



\*\*Responsável:\*\* Arquitetura Luxora



\---



\# Objetivo



Definir a estratégia oficial para armazenamento de arquivos da Luxora.



O objetivo é separar arquivos da base de dados principal, garantindo maior desempenho, escalabilidade e facilidade de gerenciamento.



\---



\# Contexto



A Luxora armazenará diversos tipos de arquivos ao longo da operação.



Exemplos:



\* comprovantes de pagamento;

\* documentos administrativos;

\* imagens;

\* anexos;

\* exportações de relatórios;

\* backups gerados pela aplicação;

\* arquivos enviados pelos usuários.



Esses arquivos não fazem parte das regras de negócio e não devem sobrecarregar o banco de dados.



\---



\# Problema



Guardar arquivos diretamente no PostgreSQL aumenta:



\* tamanho do banco;

\* tempo de backup;

\* custo de armazenamento;

\* tempo de restauração;

\* complexidade operacional.



Era necessário separar o armazenamento de dados estruturados do armazenamento de arquivos.



\---



\# Alternativas Avaliadas



\## Alternativa 1 — Arquivos no PostgreSQL



\### Vantagens



\* implementação simples.



\### Desvantagens



\* banco cresce rapidamente;

\* backups mais lentos;

\* pior desempenho.



\*\*Decisão:\*\* Rejeitada.



\---



\## Alternativa 2 — Sistema de arquivos local



\### Vantagens



\* simples;

\* baixo custo inicial.



\### Desvantagens



\* baixa escalabilidade;

\* risco de perda em caso de falha;

\* difícil replicação.



\*\*Decisão:\*\* Rejeitada.



\---



\## Alternativa 3 — Object Storage



Utilizar um serviço especializado para armazenar arquivos.



Exemplos:



\* Amazon S3

\* Cloudflare R2

\* Google Cloud Storage

\* MinIO (ambiente próprio)



\### Vantagens



\* alta disponibilidade;

\* escalabilidade praticamente ilimitada;

\* baixo custo;

\* integração simples;

\* armazenamento independente da aplicação.



\### Desvantagens



\* infraestrutura adicional;

\* dependência de um serviço de armazenamento.



\*\*Decisão:\*\* Aprovada.



\---



\# Decisão



A Luxora utilizará Object Storage como solução oficial para armazenamento de arquivos.



O PostgreSQL armazenará apenas os metadados necessários para localizar cada arquivo.



\---



\# Papel do PostgreSQL



O banco armazenará apenas informações como:



\* FileID;

\* TenantID;

\* Nome original;

\* Nome interno;

\* Tipo do arquivo;

\* Tamanho;

\* URL ou chave do objeto;

\* Data de envio;

\* Usuário responsável.



O conteúdo do arquivo nunca será armazenado no banco.



\---



\# Papel do Object Storage



O Object Storage será responsável por armazenar o conteúdo físico dos arquivos.



Exemplos:



\* PDFs;

\* imagens;

\* comprovantes;

\* documentos;

\* arquivos exportados.



\---



\# Organização



Os arquivos deverão ser organizados por Tenant.



Exemplo:



```text

tenant-001/



pagamentos/



comprovantes/



relatorios/



documentos/



tenant-002/



...

```



Essa organização facilita auditoria, backups e futuras migrações.



\---



\# Segurança



Todo acesso aos arquivos deverá respeitar:



\* autenticação;

\* autorização;

\* Tenant;

\* permissões.



Arquivos privados nunca poderão ser acessados diretamente por URL pública.



Sempre que possível, serão utilizadas URLs temporárias (Signed URLs).



\---



\# Exclusão



A exclusão de arquivos deverá seguir o fluxo:



1\. validar permissão;

2\. remover o registro do banco;

3\. remover o objeto do Storage;

4\. registrar auditoria.



\---



\# Backup



O Object Storage deverá possuir política própria de redundância.



O Backup do PostgreSQL não será responsável pelos arquivos.



Cada camada possuirá sua estratégia de recuperação.



\---



\# Benefícios Esperados



A adoção de Object Storage proporcionará:



\* banco de dados menor;

\* backups mais rápidos;

\* maior escalabilidade;

\* redução de custos;

\* melhor desempenho.



\---



\# Riscos



Os principais desafios são:



\* gerenciamento das permissões;

\* sincronização entre banco e armazenamento;

\* dependência da disponibilidade do serviço.



Esses riscos serão mitigados por auditoria, monitoramento e rotinas de verificação.



\---



\# Consequências



\## Positivas



\* Separação clara entre dados e arquivos.

\* Melhor desempenho do PostgreSQL.

\* Escalabilidade praticamente ilimitada.

\* Facilidade para migração de provedores.



\## Negativas



\* Infraestrutura adicional.

\* Necessidade de sincronizar metadados e arquivos.



\---



\# Impacto na Arquitetura



Esta decisão influencia diretamente:



\* Backend;

\* PostgreSQL;

\* Segurança;

\* Auditoria;

\* Backup;

\* Monitoramento;

\* Deploy.



Todos os módulos deverão utilizar a camada oficial de armazenamento, nunca acessando o provedor diretamente.



\---



\# Evolução Futura



A arquitetura permitirá trocar o provedor de armazenamento sem alterar o domínio.



Inicialmente poderão ser utilizados:



\* Amazon S3;

\* Cloudflare R2;

\* MinIO.



Novos provedores poderão ser adicionados através de adaptadores na camada de infraestrutura.

\* Definido PostgreSQL apenas para metadados.

\* Estabelecida organização por Tenant e uso de URLs temporárias para acesso seguro.



\---



\# Considerações Finais



O Object Storage foi escolhido por oferecer uma solução escalável, segura e independente para armazenamento de arquivos.



Essa decisão mantém o PostgreSQL focado em dados estruturados, reduz custos operacionais e prepara a Luxora para crescer sem comprometer o desempenho da plataforma.



A separação entre dados e arquivos reforça um dos princípios centrais da arquitetura: \*\*cada componente deve possuir uma única responsabilidade e evoluir de forma independente\*\*.
