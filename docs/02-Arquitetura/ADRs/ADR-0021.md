# ADR-0021 — Fronteira entre o Motor Operacional e o n8n

**Status:** Aprovada

**Versão:** 1.0

**Data:** Julho de 2026

**Responsável:** Arquitetura Luxora

---

# Objetivo

Este documento registra a decisão arquitetural sobre a divisão de responsabilidades entre o **Motor Operacional** (núcleo de decisão da plataforma, ver ADR-0001) e o **n8n** (ferramenta de orquestração de automações), preenchendo uma lacuna que não estava coberta por nenhuma ADR anterior.

---

# Contexto

O n8n é citado na documentação institucional da Luxora como o mecanismo oficial de automação, mas nunca havia sido definido tecnicamente onde ele se encaixa na arquitetura. Sem essa definição, existe o risco real de que lógica de negócio migre silenciosamente para dentro de workflows visuais do n8n, o que contraria diretamente o **Princípio 04** já estabelecido em `00-Principios-Arquiteturais.md`: *"toda regra pertence ao Domínio"*.

---

# Problema

Ferramentas de automação visual (n8n, Zapier, Make) são extremamente convenientes para conectar sistemas, mas tendem a acumular decisões de negócio dentro de seus próprios workflows ao longo do tempo — especialmente sob pressão de prazo, quando é mais rápido adicionar um nó de condição no n8n do que abrir um Caso de Uso novo no Backend. Isso cria dois lugares onde a mesma regra pode existir, divergir, e se tornar impossível de auditar de forma centralizada.

---

# Decisão

A Luxora adota o seguinte princípio de fronteira:

> **O Motor Operacional decide. O n8n executa o que já foi decidido.**

## Pertence ao Motor Operacional (dentro do Domínio, versionado, testado, auditável)

- Qualquer lógica que determine **se** uma ação deve ocorrer.
  - Exemplos: "esta cobrança deve ser enviada agora, dada a política da clínica?", "este horário pode ser oferecido ao paciente?", "este paciente deve entrar em follow-up?".
- Toda regra que varia por política configurável de clínica (cobrança, cancelamento, confirmação, tom de comunicação).
- Cálculo financeiro, verificação de conflito de agenda, elegibilidade de qualquer fluxo administrativo.

## Pertence ao n8n (orquestração, sem decisão de negócio)

- Qualquer lógica que **execute** uma ação cuja decisão já foi tomada pelo Motor Operacional.
  - Exemplos: disparar uma mensagem específica já definida no WhatsApp, sincronizar um evento já confirmado com o Google Calendar, acionar um webhook de um parceiro externo.
- Integrações com serviços externos que não possuem regra de negócio própria.
- Agendamento técnico de disparo (o "quando" já foi decidido pelo Motor Operacional; o "efetivamente disparar" é responsabilidade do n8n).

## Teste de aceite

Todo novo workflow de n8n deve passar pelo seguinte teste antes de ser aprovado em revisão:

> *"Se este workflow fosse removido e substituído por outra ferramenta de automação amanhã, alguma regra de negócio se perderia?"*

Se a resposta for **sim**, a lógica está no lugar errado e deve ser movida para um Caso de Uso dentro do Motor Operacional, com o n8n apenas invocando esse Caso de Uso via API interna.

---

# Consequências

- Toda automação n8n deve consumir APIs internas da Luxora (nunca acessar o banco de dados diretamente), preservando o princípio de que o Frontend/Automação nunca acessa o banco sem passar pelo Backend.
- O n8n é tratado, arquiteturalmente, como **mais um cliente da API** — equivalente a um canal de comunicação — e não como uma camada de decisão.
- Revisões de código/workflow devem aplicar o teste de aceite acima como critério obrigatório.

---

---

# Conclusão

O n8n permanece como ferramenta oficial de automação da Luxora, mas com uma fronteira explícita: decisão de negócio nunca sai do Motor Operacional. Essa ADR deve ser usada como critério de revisão a partir de sua aprovação.
