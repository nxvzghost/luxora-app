# ADR-0004 — Adoção de Arquitetura Multi-Tenant baseada em TenantID

**Status:** Aprovada

**Versão:** 1.0

**Data:** Julho de 2026

**Responsável:** Arquitetura Luxora

---

# Objetivo

Este documento registra a decisão arquitetural de implementar a Luxora utilizando uma arquitetura **Multi-tenant baseada em TenantID**, permitindo que milhares de clínicas utilizem a mesma plataforma mantendo isolamento completo de dados, configurações e operações.

Esta decisão é fundamental para garantir escalabilidade, redução de custos operacionais e facilidade de evolução da plataforma.

---

# Contexto

A Luxora foi concebida como uma plataforma SaaS.

Isso significa que uma única aplicação deverá atender inúmeras clínicas simultaneamente.

Cada clínica possui:

* pacientes próprios;
* terapeutas próprios;
* políticas administrativas próprias;
* agenda própria;
* mensagens próprias;
* configurações próprias;
* histórico financeiro próprio.

Apesar disso, todas utilizam exatamente o mesmo software.

Era necessário definir como garantir esse isolamento.

---

# Problema

Existem diferentes formas de construir um sistema SaaS.

Cada abordagem possui vantagens e limitações.

A decisão deveria equilibrar:

* segurança;
* custo;
* facilidade de manutenção;
* escalabilidade;
* simplicidade operacional.

---

# Alternativas Avaliadas

## Alternativa 1 — Uma aplicação para cada clínica

Cada cliente possui sua própria instalação.

### Vantagens

* isolamento físico completo;
* personalização máxima.

### Desvantagens

* custo extremamente elevado;
* deploy individual;
* atualizações lentas;
* manutenção complexa;
* baixa escalabilidade.

**Decisão:** Rejeitada.

---

## Alternativa 2 — Banco de dados separado por clínica

Uma única aplicação utilizando vários bancos.

### Vantagens

* excelente isolamento;
* backups individuais.

### Desvantagens

* grande complexidade operacional;
* gerenciamento difícil;
* migrações demoradas;
* aumento significativo de custos.

**Decisão:** Rejeitada para a fase inicial.

Poderá ser utilizada futuramente para grandes clientes.

---

## Alternativa 3 — Schema separado por clínica

Cada Tenant possui seu próprio schema.

### Vantagens

* bom isolamento;
* administração relativamente simples.

### Desvantagens

* crescimento da quantidade de schemas;
* migrações mais complexas;
* maior esforço operacional.

**Decisão:** Rejeitada para o estágio inicial.

---

## Alternativa 4 — Banco compartilhado com TenantID

Todas as clínicas compartilham o mesmo banco.

Cada registro pertence obrigatoriamente a um Tenant.

### Vantagens

* baixo custo;
* excelente escalabilidade;
* manutenção simplificada;
* deploy único;
* evolução contínua.

### Desvantagens

* exige rigor absoluto no isolamento dos dados;
* qualquer falha de implementação pode gerar vazamento entre Tenants.

**Decisão:** Aprovada.

---

# Decisão

A Luxora adotará oficialmente o modelo:

**Banco Compartilhado + Schema Compartilhado + TenantID Obrigatório.**

Toda informação armazenada deverá pertencer a um Tenant.

Nenhuma entidade administrativa existirá sem vínculo com uma clínica.

---

# Modelo de Dados

Todas as entidades principais possuirão um campo obrigatório:

```text
TenantID
```

Exemplos:

* Clínica
* Terapeuta
* Paciente
* Sessão
* Agenda
* Cobrança
* Pagamento
* Mensagem
* Follow-up
* Auditoria
* Configuração

Toda consulta deverá utilizar esse identificador como filtro principal.

---

# Contexto do Tenant

Cada requisição autenticada carregará automaticamente o contexto da clínica.

Fluxo:

```text
Login

↓

JWT

↓

TenantID

↓

Operational Engine

↓

Casos de Uso

↓

Repositórios

↓

Banco de Dados
```

O Tenant será conhecido durante toda a execução da operação.

---

# Configuração por Clínica

Cada Tenant poderá configurar seu próprio ambiente.

Exemplos:

* duração das sessões;
* política de cobrança;
* política de cancelamento;
* mensagens automáticas;
* horários de funcionamento;
* tom da IA;
* idioma;
* integrações.

Essas configurações nunca afetarão outras clínicas.

---

# Segurança

Toda operação deverá validar obrigatoriamente:

* autenticação;
* Tenant;
* permissões;
* contexto.

Mesmo conhecendo um identificador válido de outra clínica, um usuário jamais poderá acessar esses dados.

---

# Auditoria

Todos os registros de auditoria deverão conter:

* TenantID;
* UserID;
* horário;
* operação;
* resultado.

Isso permitirá rastrear todas as ações por clínica.

---

# Escalabilidade

Essa estratégia permite crescimento progressivo:

* 1 clínica;
* 10 clínicas;
* 100 clínicas;
* 1.000 clínicas;
* 10.000 clínicas;
* 100.000 clínicas.

Sem necessidade de alterar a arquitetura principal.

---

# Evolução Futura

Caso determinados clientes exijam isolamento dedicado, a arquitetura permitirá migração gradual para:

* banco dedicado;
* cluster dedicado;
* infraestrutura dedicada.

Essa evolução deverá ocorrer preservando o domínio e o Operational Engine.

---

# Benefícios Esperados

A adoção do modelo Multi-tenant proporcionará:

* menor custo operacional;
* deploy único;
* atualizações centralizadas;
* escalabilidade horizontal;
* facilidade de manutenção;
* crescimento sustentável.

---

# Riscos

Os principais riscos identificados são:

* falhas na filtragem por Tenant;
* vazamento de dados entre clínicas;
* erros em consultas SQL ou ORM.

Esses riscos serão mitigados por:

* filtros automáticos;
* testes específicos de isolamento;
* auditoria;
* validações em todas as camadas.

---

# Consequências

## Positivas

* Plataforma única para todos os clientes.
* Menor custo de infraestrutura.
* Evolução simplificada.
* Escalabilidade para milhares de clínicas.
* Gestão centralizada.

## Negativas

* Maior rigor na implementação.
* Necessidade de testes permanentes de isolamento.
* Maior responsabilidade da camada de autenticação.

---

# Impacto na Arquitetura

Esta decisão influencia diretamente:

* Banco de Dados;
* Backend;
* APIs;
* Autenticação;
* Segurança;
* Auditoria;
* Filas;
* Monitoramento;
* IA;
* Deploy.

Todas essas camadas deverão considerar o Tenant como parte obrigatória do contexto de execução.

# Considerações Finais

A arquitetura Multi-tenant baseada em TenantID foi escolhida por oferecer o melhor equilíbrio entre custo, simplicidade operacional, segurança e capacidade de crescimento.

Essa decisão permitirá que a Luxora atenda desde uma única clínica até uma operação nacional ou internacional utilizando a mesma base tecnológica, preservando a independência operacional de cada cliente e mantendo a plataforma preparada para evoluções futuras.
