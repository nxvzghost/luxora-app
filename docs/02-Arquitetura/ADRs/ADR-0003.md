\# ADR-0003 — Adoção de Clean Architecture



\*\*Status:\*\* Aprovada



\*\*Versão:\*\* 1.0



\*\*Data:\*\* Julho de 2026



\*\*Responsável:\*\* Arquitetura Luxora



\---



\# Objetivo



Este documento registra a decisão arquitetural de adotar \*\*Clean Architecture\*\* como padrão oficial de organização do código da Luxora.



O objetivo é garantir que o domínio da plataforma permaneça independente de tecnologias, frameworks, banco de dados e provedores externos.



A arquitetura deverá permitir que componentes tecnológicos evoluam sem comprometer as regras de negócio.



\---



\# Contexto



A Luxora será uma plataforma de longa duração.



Ao longo dos anos, será natural substituir tecnologias.



Exemplos:



\* trocar o modelo de IA;

\* substituir o ORM;

\* mudar o banco de dados;

\* alterar o framework web;

\* adicionar novos canais de comunicação;

\* integrar novos gateways de pagamento.



Nenhuma dessas mudanças deverá obrigar a reescrever o domínio da plataforma.



\---



\# Problema



Em muitos projetos, as regras de negócio ficam misturadas com detalhes técnicos.



Exemplo:



```text

Controller



↓



Service



↓



Prisma



↓



OpenAI



↓



WhatsApp



↓



Banco

```



Nesse modelo:



\* Controllers executam regras.

\* Services conhecem banco.

\* Banco influencia o domínio.

\* APIs externas tornam-se dependências centrais.



Quando uma tecnologia muda, grande parte do sistema precisa ser modificada.



Esse acoplamento reduz a capacidade de evolução do produto.



\---



\# Alternativas Avaliadas



\## Alternativa 1 — Arquitetura em Camadas Tradicional



Separação por:



\* Controller

\* Service

\* Repository



\### Vantagens



\* simples;

\* conhecida pela maioria das equipes.



\### Desvantagens



\* regras espalhadas;

\* Services excessivamente grandes;

\* forte dependência de tecnologias.



\*\*Decisão:\*\* Rejeitada.



\---



\## Alternativa 2 — MVC Tradicional



Modelo clássico de aplicações web.



\### Vantagens



\* rapidez para iniciar.



\### Desvantagens



\* pouca separação entre domínio e infraestrutura;

\* crescimento desorganizado em aplicações complexas.



\*\*Decisão:\*\* Rejeitada.



\---



\## Alternativa 3 — Clean Architecture



Separação por responsabilidade, com dependências apontando sempre para o núcleo do domínio.



\### Vantagens



\* baixo acoplamento;

\* alta testabilidade;

\* facilidade para substituir tecnologias;

\* maior vida útil da plataforma.



\### Desvantagens



\* arquitetura inicial mais complexa;

\* exige disciplina de implementação.



\*\*Decisão:\*\* Aprovada.



\---



\# Decisão



A Luxora adotará oficialmente o modelo de Clean Architecture.



Toda dependência deverá apontar para o domínio.



O domínio nunca conhecerá:



\* banco de dados;

\* framework;

\* APIs externas;

\* provedores de IA;

\* interface gráfica.



\---



\# Estrutura Arquitetural



```text

┌───────────────────────────────┐

│ Interface (Frontend / APIs)   │

└──────────────┬────────────────┘

&#x20;              │

&#x20;              ▼

┌───────────────────────────────┐

│ Casos de Uso (Application)    │

└──────────────┬────────────────┘

&#x20;              │

&#x20;              ▼

┌───────────────────────────────┐

│ Domínio                       │

│ Entidades                     │

│ Objetos de Valor              │

│ Serviços de Domínio           │

└──────────────┬────────────────┘

&#x20;              │

&#x20;              ▼

┌───────────────────────────────┐

│ Infraestrutura                │

│ Banco                         │

│ IA                            │

│ WhatsApp                      │

│ Redis                         │

└───────────────────────────────┘

```



A regra fundamental é:



\*\*As dependências sempre apontam para dentro.\*\*



\---



\# Organização do Backend



A estrutura oficial seguirá o padrão:



```text

modules/



appointments/



domain/



use-cases/



repositories/



controllers/



services/



events/



validators/

```



Cada módulo será independente.



\---



\# Inversão de Dependência



O domínio dependerá apenas de interfaces.



Exemplo:



O domínio conhece:



```text

IPaymentGateway

```



Mas não conhece:



```text

Mercado Pago



Stripe



Asaas

```



A implementação concreta será fornecida pela infraestrutura.



\---



\# Benefícios Esperados



A adoção da Clean Architecture proporcionará:



\* independência tecnológica;

\* facilidade para testes;

\* menor acoplamento;

\* maior reutilização;

\* evolução contínua;

\* manutenção simplificada.



\---



\# Riscos



Os principais desafios desta decisão são:



\* maior número de arquivos;

\* curva de aprendizado para novos desenvolvedores;

\* necessidade de disciplina arquitetural.



Esses desafios são compensados pela facilidade de evolução da plataforma.



\---



\# Consequências



\## Positivas



\* O domínio permanece protegido.

\* Frameworks podem ser substituídos.

\* IA pode evoluir sem alterar regras.

\* Banco pode ser migrado.

\* APIs externas tornam-se detalhes de implementação.



\## Negativas



\* Arquitetura inicial mais extensa.

\* Maior esforço de documentação.

\* Mais abstrações.



\---



\# Relação com o Operational Engine



O Operational Engine faz parte da camada de aplicação.



Ele coordena Casos de Uso, consulta políticas e orquestra a execução.



As regras continuam pertencendo ao domínio.



Essa separação evita que o Motor Operacional concentre lógica de negócio indevidamente.



\---



\# Relação com Domain-Driven Design



DDD e Clean Architecture são complementares.



DDD define:



\* o que é o domínio;

\* quais são as entidades;

\* quais regras existem.



Clean Architecture define:



\* onde cada componente fica;

\* como as dependências são organizadas;

\* como preservar a independência do domínio.



\---



\# Impacto na Plataforma



Esta decisão influencia diretamente:



\* Backend;

\* APIs;

\* Banco de Dados;

\* Serviços;

\* IA;

\* Filas;

\* Monitoramento;

\* Deploy.



Toda implementação deverá respeitar os limites entre as camadas.

\# Considerações Finais



A Clean Architecture foi escolhida porque permite que a Luxora evolua durante muitos anos sem depender de uma tecnologia específica.



Frameworks, bancos de dados, provedores de IA e integrações poderão ser substituídos conforme a plataforma crescer, preservando o ativo mais importante da empresa: \*\*o conhecimento do domínio administrativo das clínicas de saúde mental\*\*.



Essa decisão garante que a Luxora permaneça sustentável, testável e preparado para crescer sem perder qualidade arquitetural.
